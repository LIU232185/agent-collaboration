# MAS-Resilience：看板机制实验

来源：[ICML 2025 论文](https://proceedings.mlr.press/v267/huang25ay.html)、[官方代码和数据](https://github.com/CUHK-ARISE/MAS-Resilience)。本地 upstream 固定提交 `e7704b9cbb2e47bef9e651d1709aeacfbd6ff48c`，仅作为阅读参考，未导入或运行其代码。官方代码 GPL-3.0，原许可证保留在 upstream；看板模块为独立编写的规则实现。

论文区分两类故障：AutoTransform 改写角色配置，AutoInject 改写传递中的消息。Challenger 使接收者质疑消息，Inspector 额外拦截检查消息。本文实现借用这些设计思路，不实现论文的 LLM 自动注错与模型防御，也没有重跑其六个系统、四类任务或恢复率结果。

本地入口：`npm run board`，访问 http://127.0.0.1:4322 ，勾选“启用故障与恢复实验”。

## 实际执行内容

以采购总价为受控案例，数量和单价由用户给定。计算员先计算，然后按选择将总价多加一件或删除依据，留下不可覆盖的消息版本。原始题目保留在检查器输入中。检查器只读取题目和候选消息，独立乘法验算，不读取注错标记或保存的正确输出。

- 无防护：接收方按对照条件直接采用上游结果；错误可能进入最终交付。
- Challenger：接收方在使用前质疑并验算，发现不符后隔离、退回重算，再次验证才继续。
- Inspector：新增独立规则检查节点，在业务接收方消费消息前检查并触发修复。
- 两者结合：两个检查阶段都执行。若 Inspector 已修复，Challenger 对新版本再次检查，不重复制造故障。

最多允许一次重算，也可以将恢复预算设为零以观察阻断。无法修复时最终节点不运行；阻断不算修复成功。无防护组仍有原有“审查员”位置，但在本实验中被明确配置为直接接受，用来隔离研究保护机制的作用。

最终外部验算发生在交付之后，只评分，不回写或修正无防护组。检查金额与数量、单价依据两项；金额正确但缺失依据也判不通过。异常交接次数统计所有不符合原题的已传递候选，包括送达 Inspector 的隔离检查输入，因此不是“受污染的业务智能体数量”。

主运行结束后，以相同原题、故障和恢复预算分别真实执行四个独立、无 API 的对照运行。看板展示最终金额、是否检出、修复、阻断及异常交接次数；导出 JSON 包含完整四组 comparisonTrials 证据。每组只有一个受控样本，不呈现统计恢复率，也不能外推到语言模型能力。

## 与官方实现的核对

官方 `Defense/Inspector.py` 保存历史并调用 `gpt-3.5-turbo-0125`，依据 JSON 决定返回原文或 revision。`Defense/Challenger.py` 在 `act(last_message)` 中调用带占位符的 `challenger_prompt.format()` 却未传参，且未使用 last_message；直接运行存在格式化问题。README 中示例方法参数也与实际签名不同。当前不照搬这些入口。

本地增加的隔离状态、预算、消息版本链、重算和失败阻断属于工程恢复设计，不应归为论文已验证结论。论文中的性能恢复数字也不等同于逐条消息的纠错准确率。

验证：`node --test board/engine.test.mjs board/resilience.test.mjs`，不读取 API 密钥或调用模型。
