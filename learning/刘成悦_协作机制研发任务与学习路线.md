# 刘成悦：协作机制研发任务与学习路线

更新日期：2026-10-20

## 你负责什么

你和黄镜桦共同负责项目③“协作机制研发”。你们的目标是让规划者、执行者、反思者能够围绕一个真实任务协同工作：决定任务怎么分、由谁处理、结果如何传下去、发现问题后如何处理。

你们不负责把三个 Agent 各自变聪明，也不负责共享记忆与经验进化；这些由 Agent 能力组、进化机制组负责。你们要先把 Agent 之间的合作方式定清楚，再接入可调用的 Agent。

最核心的问题可以这样表达：

> 给定一个具体任务，系统怎样决定谁做什么，怎样判断阶段结果可用，以及失败后如何恢复或停止？

## 可以并行推进，不必等 Agent 完成

项目 ② Agent 能力研发和项目 ③ 协作机制研发是并行任务。你的个人顺序可以是“先学习和形成协作方案，再做 POC”。在你学习期间，Agent 能力组可以并行搭建角色。等你开始 POC 时，若真实 Agent 已就绪就直接集成；若尚未就绪，用模拟 Agent 验证协作规则，无需把自己的工作整体停下来等。

建议把工作分成三个泳道：

| 现在独立推进 | 现在同步对齐 | 等 Agent 可调用后再做 |
|---|---|---|
| 阅读论文、梳理协作方案；画角色与流程；确定阶段验收；选定评测任务；实现模拟 Agent 和协作流程骨架；测试通过/失败分支 | Agent 的调用方式、输入输出字段、错误返回格式；选用同一个演示任务；谁负责维护端到端测试 | 将模拟 Agent 换成真实 Agent；检查 Prompt 输出能否满足接口；端到端试跑并调整流程 |

因此不是“等同事做完我再开始”：学习、阅读、场景梳理和协作方案设计现在就能开展；POC 放在学习之后，真实 Agent 接口和模拟接口都可作为执行载体。

## 目前要做的事

你当前的首要目标是掌握协作机制的研究问题和方案思路，先不把实现 POC 当成学习本身。按“提出问题 → 阅读证据 → 自己解释 → 用案例检查理解 → 整理成讲解文档”的顺序研究。你读到能回答本节的掌握问题之后，再决定要复现什么。

## 这项工作每一步需要掌握的知识

这六步是一条完整的协作链：先说清工作是什么，再决定怎么分、交给谁，接着管理进度和结果，最后处理错误并证明协作有价值。

### 1. 任务定义与验收

要学任务契约、输入输出、结构化结果和验收标准。任务契约要说清目标、可用资料、限制、要交付什么、如何判定完成。例如“写报告”很难验收；“根据给定资料写三条建议，每条附支持依据，缺资料时标明不确定”就可以执行和检查。结构化输出格式正确不代表内容正确，因此格式检查和事实/质量验收要分开。

**自测：**能把“请分析一下这个问题”改写成有明确输入、产物和通过标准的工作说明吗？

### 2. 任务拆分

要学任务粒度、依赖关系、DAG（有向无环图）、前置条件与完成条件。拆分的目的，是让每个子任务都有明确产物、可以单独验收；太粗会导致失败后大段重做，太碎会增加沟通和协调成本。依赖图用来判断先后顺序：没有依赖的任务可考虑并行；下游任务必须等必要的上游产物验收通过。

**自测：**能把一个目标画成子任务图，指出哪些能并行、哪个上游失败会影响哪些下游吗？

### 3. 角色分配与路由

要学能力描述、硬约束与候选选择。先定义角色擅长什么、能访问哪些资料、可用哪些工具、应交付什么。权限和资料范围是硬约束，不能被“看起来很擅长”抵消；通过约束筛选后，再考虑准确性、负载、时间和费用。任务路由是选“哪个角色做”，模型路由是选“这个角色用哪个模型”，初期先学前者即可。先有单 Agent 基线，才能判断增加角色是否有必要。

**自测：**能解释为什么某任务交给某角色，并说明无合适角色时应该怎么处理吗？

### 4. 状态与进度管理

要学状态机、Run/Task/Attempt 区分、持久化和检查点。Run 是一次用户目标，Task 是其中一个子任务，Attempt 是子任务的一次尝试。状态机列明哪些状态存在、如何合法迁移，以及何时可以启动下游。检查点保存当前执行进展，长期记忆保存以后可能复用的经验，两者用途不同。

**自测：**执行者完成了上游任务，但下游失败时，能解释哪些结果保留、哪些任务重做吗？

### 5. 消息交接与结果传播

要学消息用途、交接信息、确认语义和协作拓扑。下游要拿到足够完成工作的目标、输入、约束、来源与验收要求。区分“消息送达”“任务已接受”“执行已完成”“结果已验收”。链式、中心协调、树状等结构决定了 Agent 如何互相交接；应结合依赖关系、并行需要、核验要求与成本选择。

**自测：**能为“执行者把结果交给反思者”写清需要传什么、反思者如何返回通过或问题吗？

### 6. 失败处理：重试、修正、重规划或停止

要学错误分类、错误传播、重试预算与终止条件。暂时性超时可限次重试；内容不正确需要具体反馈后修正；缺资料需要补充信息；无权限应停止或等待处理。Retry 是重新尝试同一工作，Repair 是根据反馈修改结果，Replan 是改变任务安排。若操作可能已经对外生效，超时后不能盲目重复，需先核实状态或使用有效幂等机制。每条恢复路径都应有限次、有限时、有限预算。

**自测：**遇到超时、事实错误、资料不足、无权限四种情况，能分别选对处理方式并说明何时停止吗？

### 7. 方案评估

要学基线、控制变量、质量和过程指标、成本指标及消融。至少用一个单 Agent 或执行者直出方案作基线；比较协作方案时尽量固定任务、资料、验收办法、模型和预算。记录最终通过率，也记录错误发现率、修正成功率、调用次数、耗时与失败原因。消融是拿掉一个角色或环节，检查效果变化是否来自它。少量任务适合发现问题，不足以证明普遍有效。

**自测：**能说明对照组是什么、协作改善了什么、额外成本是多少，以及数据不足时哪些结论不能下吗？

学完这七步，你应能从一个业务目标推出任务与分工方案，指出交接要求和错误处理路径，并设计公平的比较实验。先掌握这些概念，再进入 POC。

## 如何研究，才能真正掌握

### 第一步：把工作主题变成研究问题

不要从“我要实现任务拆分、路由、状态、消息、重试”这些名词开始，而是先写下系统要帮助团队作出的决定：

> 对一个具体任务，怎样决定是否拆分、分给谁、阶段结果是否可接受，以及失败后选择修正、重新分工、补充信息还是停止？

把这句话放在笔记首页。后面每读一篇文章，只提取它能回答的那部分问题。

### 第二步：先建立概念地图

先把研究范围分成四个连续问题，按顺序理解：

| 问题 | 需要掌握的概念 | 自测：不看资料能否回答 |
|---|---|---|
| 为什么需要协作 | 单 Agent 基线、任务可分解性、并行收益、沟通成本、协作适用边界 | 什么任务有理由拆给多个 Agent？何时一个 Agent 更合适？ |
| 怎样组织协作 | 子任务、角色、依赖关系、执行顺序、协作拓扑、路由依据 | 同一个目标为什么可用串行、星型或树型流程？怎么选？ |
| 怎样判断是否有效 | 任务成功、过程里程碑、沟通质量、额外成本、对照实验 | 只看最终答案够吗？对照组和预算为何要固定？ |
| 失败后怎么办 | 失败类型、错误传播、检查与挑战、修正、重规划、终止条件 | 内容错误、超时、缺资料分别应该采取什么动作？ |

先用自己的话写出每个概念的解释和一个职场例子。遇到不能解释的词，再回论文或资料查，不要只抄术语表。

### 第三步：分层阅读，而不是每篇从头读到尾

**先读综述，建立地图。** 阅读 [Beyond Self-Talk: A Communication-Centric Survey](https://arxiv.org/abs/2502.14321)，重点浏览分类框架、通信目标和挑战。产出一页“多 Agent 协作方式有哪些”的概念图。

**再读收益与边界。** 阅读 [Capable language models can outgrow the benefits of collaboration（2026）](https://www.nature.com/articles/s42256-026-01268-y)，重点看实验如何控制条件、如何与单 Agent 对照、哪些情况协作反而不划算。产出一张“值得协作 / 不一定值得协作”的条件表。

**再读协作结构和评价。** 阅读 [MultiAgentBench（ACL 2025）](https://aclanthology.org/2025.acl-long.421/)，重点看协作结构、里程碑和评价指标。产出一张“最终质量 + 过程质量 + 成本”的评价表。

**最后读路由与失败。** 阅读 [MasRouter（ACL 2025）](https://aclanthology.org/2025.acl-long.757/)理解协作方式和角色分配问题；阅读 [MAST（NeurIPS 2025）](https://neurips.cc/virtual/2025/loc/san-diego/poster/121528)以及 [ICML 2025 的韧性研究](https://proceedings.mlr.press/v267/huang25ay.html)，理解错误类别、错误传递和检查策略。产出一张“问题表现 → 可能根因 → 合适处理方式”表。

第一轮每篇只需要读摘要、问题定义、方法图、实验设计、主要结果、局限和结论。对你当前任务无关的基准实现细节先略过；遇到核心概念不懂，再回到正文查。

### 第四步：每篇文章用同一张研究卡片

每篇限制在一页以内，回答：

1. 论文要解决什么决策问题？
2. 作者提出了什么方案？用自己的图或例子重画，不复制论文措辞。
3. 作者拿什么方案作比较，评价指标是什么？
4. 哪些证据支持结论？结论在什么条件下成立？
5. 哪些局限意味着不能直接迁移到我们的职场任务？
6. 这篇文章改变了我对协作机制的哪一个判断？

论文里的提升数字先记录来源与实验条件，不把单个基准结果直接当成项目预期。优先研究“方案为什么有效/失效”，再决定是否值得复现。

### 第五步：把知识迁移到团队场景

不用调用模型，先用纸面案例推演一次“根据资料生成报告”：

- 单 Agent 会怎样做？
- 什么时候规划者拆分能产生实际价值？
- 哪个阶段需要独立检查？检查标准是什么？
- 出现超时、错误结论或资料不足时，下一步分别是什么？
- 新增 Agent 带来哪些质量收益，又增加哪些调用和交接成本？

把每个回答标成“论文证据”“团队当前假设”或“尚待验证”。这样就不会把文献结论、个人设计选择和实验结果混成一件事。

### 第六步：整理成给别人讲的学习文档

学习文档不以代码或组件清单为主，应按听众理解问题的顺序组织：

1. 协作机制解决什么问题，为什么不能只看 Agent 个体能力。
2. 多 Agent 什么时候有用，什么时候可能不划算。
3. 一个职场任务如何被组织成合作过程。
4. 怎样评价协作结果与过程。
5. 常见失败类型和对应处理思路。
6. 我们团队目前的方案假设、未验证问题与后续实验。

每个主要结论都说明它来自论文证据、团队方案还是尚未验证的假设，并附原始论文链接。

### 什么时候算掌握

进入 POC 前，先检查自己能否不看论文完成下面四项：

1. 用 3 分钟讲清为什么“多 Agent”本身不保证更好。
2. 针对一个职场任务，画出单 Agent 与一个多 Agent 方案，并解释为何选它。
3. 设计一个公平的对照，讲清质量、过程和成本各怎么衡量。
4. 给超时、内容错误、资料不足各提出不同处理办法，并说明理由。

如果讲不清，回到对应研究问题补读，不必为了“读完几篇”就急着实现。

## POC 放在学习之后

达到上面的掌握标准，再用 POC 检验自己的判断。Agent 能力组可以并行开发；你开始 POC 时，真实 Agent 已就绪就集成，尚未就绪就用模拟角色先检验流程。模拟 POC 验证的是规则和流程，不代表已经掌握 LLM 的协作效果。

### 1. 学习期间选定一个演示任务

先自行拟定一个可重复验证的任务，例如“根据给定资料整理结论、列出依据并检查结论”。再和 Agent 能力组、实验评估负责人快速对齐是否能代表项目目标。任务应有明确输入、可核对结果，而且能人为构造错误。

不要一开始同时支持所有职场任务。先挑一个代表性任务，把流程做清楚。

### 2. 学完基础后设计合作方案

围绕选定任务，写清下面四件事：

| 要决定的事 | 需要回答的问题 |
|---|---|
| 任务怎么分 | 哪些工作由规划者、执行者、反思者承担？哪些环节可省略？ |
| 结果怎么交接 | 每个阶段要把什么交给下一阶段？ |
| 怎样算合格 | 哪些标准由程序检查，哪些需要反思者判断？ |
| 问题如何处理 | 是修正、补充资料、重新分工、重做，还是停止并说明原因？ |

输出一张简洁的流程图和一页协作规则。初版可先比较两种方案：执行者直接产出最终答案；执行者产出后由反思者检查。

### 3. 学习期间同步对齐团队接口

和 Agent 能力组约定每个 Agent 的输入、输出和失败反馈；和实验评估组约定任务与评分标准；和测试工程组约定日志以及端到端验收方法。

协作层消费 Agent 的能力，不替代 Agent 的内部实现。评估与测试团队负责衡量结果；你们负责让可比较的流程实际跑起来。

### 4. 掌握概念后再用模拟 Agent 跑通最小协作流程

先用脚本或规则模拟规划者、执行者、反思者的输入输出，完成“规划 → 执行 → 反思检查 → 通过或处理失败”的闭环。可以让模拟执行者第一次故意漏掉证据，让模拟反思者指出问题，再观察流程是否按约定修正或停止。

这样现在就能验证：流程分支有没有设计完整、阶段验收是否可执行、失败路径是否可解释、评价指标能否记录。已有的 [coordination_lab.py](coordination_lab.py) 已包含确定性角色的部分机制，可作为参考或基础。

模拟 Agent 不能回答“真实模型会不会拆好任务、判断对不对”。所以当前 POC 验证的是协作流程设计；真实 Agent 准备好以后，再替换模拟调用，进行 Prompt 和端到端集成验证。

### 5. 比较方案并汇报结论

先用模拟输出和注入错误检查评分标准、错误路径和记录方式是否合理；随后使用相同任务、评分标准和资源预算，对比“执行者直出”和“执行者加反思检查”。真实 Agent 尚未完成时，不需要等待才能设计实验表与评分规则。至少记录任务成功率、错误发现率、修正后通过率、调用次数或费用、耗时。

如果反思检查没有稳定改善结果，或提升小于额外成本，就要如实报告并简化流程。实验结论只适用于当前任务集，不直接代表所有职场场景。

## 建议的近期产物

1. 一页演示任务说明：输入、期望结果与验收标准。
2. 一张协作流程图：角色、分工、阶段结果和异常去向。
3. 一份 Agent 交接约定：各阶段的输入和输出由团队共同确认。
4. 一个可反复运行的最小 Demo：至少展示一次成功流程和一次失败处理。
5. 一张结果表：对比至少两种协作方案及资源成本。
6. 一份讲解材料：说明问题、方案、实验和适用边界。

前四项可以在 Agent 能力组开发期间推进；真实端到端结果与成本结论需要等接口可用后补齐。这些是建议产物；本文件没有宣称上述工作已经完成。

## 推荐阅读：先理解问题，再看机制

### 第一篇：先判断什么时候需要多 Agent

[Capable language models can outgrow the benefits of collaboration（Nature Machine Intelligence，2026）](https://www.nature.com/articles/s42256-026-01268-y)

该研究在多种模型、任务和协作架构之间做受控比较，也包括职场任务。它帮助回答“加 Agent 是否会有收益”，而不是假设 Agent 越多越好。阅读时关注对照条件、任务与资源预算如何控制，以及协作开销如何纳入判断。

### 第二篇：了解怎样评价协作过程

[MultiAgentBench: Evaluating the Collaboration and Competition of LLM Agents（ACL 2025）](https://aclanthology.org/2025.acl-long.421/)

文章比较 star、chain、tree、graph 等协作结构，并通过中间里程碑衡量协作。官方实现：[MARBLE 代码与数据](https://github.com/ulab-uiuc/MARBLE)。可借鉴其评价思路；完整基准包含多种环境，复现工作量较大，初期先做小型任务集上的结构对照。

### 第三篇：建立失败诊断框架

[Why Do Multi-Agent LLM Systems Fail?（NeurIPS 2025 Spotlight）](https://neurips.cc/virtual/2025/loc/san-diego/poster/121528)

论文分析多种系统的执行轨迹，整理出 14 类失败模式，涵盖系统设计、Agent 配合、任务验证。官方项目和数据：[MAST](https://github.com/multi-agent-systems-failure-taxonomy/MAST)。阅读时，把失败分类映射到你们流程中“任务设计、角色交接、结果检查、结束条件”这些环节。

### 第四篇：从沟通角度看多 Agent 全景

[Beyond Self-Talk: A Communication-Centric Survey of LLM-Based Multi-Agent Systems（2025，2026 年修订）](https://arxiv.org/abs/2502.14321)

这是一篇综述，从通信架构、目标、协议、策略和消息内容梳理多 Agent 协作研究。适合建立地图和查术语，不需要从头到尾精读。可重点浏览架构、消息策略、评价挑战和局限。

### 路由补充

[MasRouter: Learning to Route LLMs for Multi-Agent Systems（ACL 2025）](https://aclanthology.org/2025.acl-long.757/) 把选择协作方式、分配角色、选择模型作为连续决策。它和你的路由职责相关；官方代码在[这里](https://github.com/yanweiyue/masrouter)。在最小流程跑通之前，把论文算法完整搬进来不是首要工作。

## 阅读时要带着的问题

每篇文章读完，用几句话回答：

1. 作者要解决什么实际问题？
2. 它比较了哪些方案，控制了哪些因素？
3. 结果说明什么时候这种协作方式有用，什么时候可能不划算？
4. 哪种方法可迁移到我们的演示任务？
5. 我们需要怎样的实验才能判断迁移后是否有效？

先读 Nature 文章，明确评估问题；接着读 MultiAgentBench，学习比较协作结构；然后读 MAST，学习解释失败；最后用综述补全概念地图。MasRouter 可作为路由专题。

## 学习后再做小型 POC：真实 Agent 优先，模拟 Agent 兜底

### 问题

“加入反思检查，能否提高我们演示任务的最终通过率？提升是否值得额外调用？”

### POC 第一步：验证机制流程

- 先自己准备 3—5 个带有明确验收答案的任务草例，之后再与评估组的 10 题集合并或替换。
- 用简单规则模拟规划者产出固定计划、执行者产出固定结果、反思者核查确定性条件。
- 方案 A：执行者结果直接结束。
- 方案 B：反思者检查；遇到预设错误时，返回一条固定反馈，执行者按脚本修正一次。
- 注入几类已知问题，例如遗漏证据、数字不符、格式不符合验收条件。
- 确认每类情况最终会通过、修正、等待补充信息或明确失败，并且轨迹能解释原因。

如果届时真实 Agent 还没准备好，可先用模拟角色完成这一步。它不衡量 LLM 能力高低，目标是检验“合作规则是否清楚、流程是否闭环、指标是否可收集”。

### POC 第二步：真实 Agent 集成评估

- 接入 Agent 能力组提供的真实规划者、执行者和反思者。
- 保持同一批题目与评分标准，对比直出和反思检查。
- 记录 Agent 是否遵守输入输出契约、真实成功率、错误发现率、修正成功率、调用成本和耗时。
- 将真实结果与模拟结果区分报告。模型随机性需要重复运行并记录模型版本和参数。

### 记录

| 指标 | 说明 |
|---|---|
| 最终通过率 | 通过既定任务验收标准的任务数占比 |
| 错误发现率 | 注入错误中被反思者识别出来的比例 |
| 修正成功率 | 被发现的错误中最终修正并通过验收的比例 |
| 额外成本 | 相较直出方案新增的模型调用、费用和耗时 |
| 失败原因 | 任务划分、Agent 输出、消息交接、反思判断或验收规则等 |

模拟阶段只报告流程机制验证结果；真实 Agent 阶段的小规模试验用于发现问题，不用 10 道题的数据宣称普遍效果或统计显著性。若模型输出有随机性，应重复运行并记录模型版本和参数。

### 如何说明复现程度

现在的确定性模拟可以验证“出错时流程是否分支、是否验收、是否在预算内结束”，不需要等同事的 Agent。它不能验证 LLM 是否擅长判断或修复。待真实 Agent 接入后，用自己的职场任务比较协作方式，可称为受论文启发的小型 POC；复现论文实验则要求尽量匹配论文数据、模型、方法和评估协议。

## 可以直接用于汇报的结构

1. **问题：**三个 Agent 已能独立调用，但需要明确何时分工、怎样交接、结果如何验收。
2. **方案：**展示为目标任务设计的流程，讲清每个角色的产物和异常处理。
3. **验证：**展示直出与反思检查的对照结果，以及人为注入错误后的轨迹。
4. **结论：**说明协作是否有效、付出了多少额外成本、哪些情况仍会失败。
5. **下一步：**依据结果决定是否调整角色、分工规则或检查方式。

开场可以这样说：

> 我负责多 Agent 的协作机制。我们的目标不是单纯增加角色，而是明确任务何时需要拆分、由谁完成、阶段结果如何验收，以及错误发生后怎么继续或停止。本次先在一个可重复的任务上比较两种协作方式，用实验决定反思检查是否值得加入。
