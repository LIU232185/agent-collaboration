# 给主管展示：多 Agent 编排与策略进化原型

## 解决的问题

单个业务 Agent 的能力不足以保证整条业务流程有效。客户分析、营销和风控可能有不同结论；简单串联既限制并行，又可能让上游错误逐步传播。这个原型将三团队封装为业务节点，用明确依赖组织并行执行，并将模型审查与可计算约束分开验收。

## 核心技术

### 1. 两层图编排

上层规划器根据任务选择经过校验的协作 DAG。下层每个团队包含两个并行子 Agent，顶层负责汇总。规划结果驱动真实调度，不只是修改图形连线。

```js
const ready = Object.keys(deps).filter(id =>
  !done.has(id) && deps[id].every(parent => done.has(parent))
);
await Promise.allSettled(ready.map(executeTeam));
```

代码为调度逻辑的精简讲解，实际实现见 runtime.mjs。当前支持三种图：三团队独立并行、客户完成后两团队并行、风控完成后两团队并行。不是任意图自动生成或训练后的 MasRouter。

### 2. 联合审查与独立门控

团队结论汇合后调用联合审查模型；后端另外检查原始授权、预算和有限禁用词。二者都通过才放行。修订最多一次，保留消息版本并再次调用模型复审。

```js
const gate = auditCandidate(candidate, originalFixture);
const canDeliver = gate.passed && modelReview.passed;
```

真实验证已出现“模型复审通过、预算校验失败”的冲突，任务被阻断。该记录 ID 为 `73782d26-5c2c-4ca3-92de-52e01bbb4ea0`，选择 mesh，实际完成 13 次模型调用、返回 12113 token。这个例子可用于说明为何不能让 LLM 的自我评价直接等于执行许可。硬规则范围很窄，不能宣称解决所有业务合规风险。

### 3. 从真实轨迹到候选策略

优化器读取任务、团队输出、审查结果和当前策略，调用 LLM 提出提示策略与拓扑偏好。它不是一个写死的 v2 补丁。三个未提供给优化器的固定样例分别调用基线和候选，用确定性约束计分；如实区分提升、持平和下降。

新策略需显式启用，后续任务采用新快照；旧运行不会被覆盖，可以回滚。当前评估只覆盖营销生成，不证明拓扑优化有效或模型能力增长。

首次真实进化实验共 7 次调用，固定留出约束通过数由基线 3/3 变为候选 2/3；系统禁止启用候选，保留原策略。该结果用于验证评估闸门与回退机制，不能作为能力提升证据。

第二次真实业务运行 ID 为 `0304dd02-a7e4-4236-8c93-a1decf67123f`，选择 risk_fanout，先由风控给出约束，再由客户与营销并行。12 次模型调用完成，联合审查与确定性约束均通过，并生成主管摘要。两个验证任务均在输入中明确指定了期望拓扑，因此证明的是受任务指令驱动的模型选图与执行链路，不证明规划器可以自主选出最优拓扑。

### 4. 可观测运行证据

后端记录调用起止时间、输入输出、提供方 token 用量、策略版本、图结构、反馈和错误。数据落盘，界面通过轮询展示实际事件。源码页读取当前项目的真实文件，不是装饰性代码片段。

## 演示顺序

1. 在运行历史选择真实任务，解释图结构及并行子调用。
2. 点击子 Agent 与顶层 Agent，查看调用输入输出。
3. 展示联合审查、修订和最终门控的不同职责。
4. 进入策略进化，展示源任务证据、模型提案及基线／候选评分。
5. 依据评估结论讨论是否启用，不把持平说成能力提升。
6. 切到技术实现页，查看实际后端源码与评估边界。

## 当前边界与下一步

目前是同一基础模型通过不同职责提示形成多个 Agent，使用虚构业务数据。没有接真实 CRM、真实联系客户、训练参数或复现论文指标。下一阶段应接入各业务团队接口，建立独立业务评测集，扩展门控规则，并以成功交付率、返工次数、延迟和成本共同评价，避免只看模型打分。
