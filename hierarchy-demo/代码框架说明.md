# 多 Agent Demo 代码框架说明

## 1. 这是什么
这是一个原生 Node.js HTTP 后端加 HTML/CSS/JavaScript 前端的多 Agent 编排 Demo。没有使用 React，也不是每个 Agent 都是独立服务。默认多个角色共用模型，通过提示词与上下文区分职责。

## 2. 目录与职责
- hierarchy-demo/console.html：当前页面结构。
- hierarchy-demo/console.css：当前页面样式。
- hierarchy-demo/console.mjs：按钮事件、接口请求、状态轮询与展示。
- hierarchy-demo/server.mjs：当前 Demo 的启动入口；提供页面和 API，保存历史状态。
- hierarchy-demo/paper-runtime.mjs：当前主协作引擎；团队注册、路由、依赖执行、辩论、审查和最终综合。
- hierarchy-demo/prompts.mjs：本轮原样抽出的 9 组公共提示词；包括 worker、planner、chainRouter、inspector、debate、debateAssessment、synthesis、common、formatRepair。
- hierarchy-demo/agent-adapters.mjs：默认模型、内部角色和外部 HTTP Agent 的调用适配。
- model-provider.mjs：模型配置、鉴权、请求与响应解析。
- model-network.mjs / model-transport.mjs：代理选择与网络传输。
- hierarchy-demo/runtime.mjs、engine.mjs：历史执行与模拟逻辑；当前 /api/start 使用 paper-runtime.mjs，不能把所有 runtime 都当作当前入口。
- *.test.mjs：离线回归测试，不需要模型 API。

注意：根目录也有 server.mjs，它不是本看板入口。请运行 npm run hierarchy。

## 3. 一次任务的执行流程
1. 页面 POST /api/start，提交 task、collaboration、router 等选项。
2. server.mjs 使用 createPaperRun 创建记录，保存后返回 202 与运行 ID。
3. 后台 executePaperRun 执行；自动模式选择协作方式，手动模式使用指定方式。
4. 按依赖安排三团队：customer（需求/事实）、marketing（方案/评估）、risk（权限/证据）。各团队包含两个子角色。
5. 子角色分析，团队负责人汇总；Inspector 检查团队消息。严重且有原文依据的问题触发修订，最多修订两次。仍失败则隔离原文。
6. 后续团队读取前序已审查结果。辩论模式进一步互读、回应和评估是否继续。
7. 最终综合已审查材料，再接受最终审查。
8. 后端保存状态；页面 GET /api/state 显示进展与结果。

## 4. Prompt 到底在哪里
prompts.mjs 是公共模板；paper-runtime.mjs 中的 teams 提供角色 scope、子角色 task；每次调用的 input 还包括 question、identity、assignment、upstream 等。

在 ask() 中：instructions = 当前模板 + prompts.common。格式纠正另加 prompts.formatRepair。模型收到的内容既包括 instructions，也包括 JSON 序列化后的 input；看公共模板无法看到全部上下文。

例如需求子角色使用通用 worker 模板，但 input.identity 是其团队身份，input.assignment 是“区分用户已给事实、一般机制、待验证假设与缺失信息”。因此六个子角色并不是各有一份完全独立的完整模板。

运行记录 calls 中保存 instructions、input、output 与调用元数据。适配器如果追加自定义职责，当前 calls.instructions 保存的是追加前内容，不能直接称为完整实际请求。

## 5. 主要 API
- GET /api/state：状态、历史、团队注册表和公开配置。
- GET /api/source?file=prompts.mjs：查看公共提示词源码。
- POST /api/start：启动协作。
- POST /api/cancel：取消任务。
- POST /api/agents/test：单独试运行角色。
- POST /api/agents/save：保存角色配置。
- POST /api/reload：重读模型与 Agent 配置。
- POST /api/probe：模型连通性检查。

## 6. 当前限制与需要注意的代码问题
本次仅抽取提示词并增加源码入口，没有改变协作行为。检查代码发现：paper-runtime 的子角色调用将团队 ID（如 customer）放在 args.team；agent-adapters 却使用 args.team 查找配置，而工作台按子角色 ID（如 profile）保存配置。因此“保存成功”不能证明配置已经用于正式协作；六个子角色配置可能无法命中。外部配置也有同样的匹配问题。本包保留当前实现，未夹带此项行为修复。

系统是本机 Demo，监听 127.0.0.1，没有完整用户登录与权限系统。自动路由是模型或规则选择，并非已训练路由器。离线测试通过不等于真实模型联调通过。

## 7. 启动与检查
需要 Node.js 22+；如使用代理功能建议兼容项目要求的 Node 版本。复制 .env.deepseek.example 为 .env，填写自己的配置，再运行：

```bash
npm run hierarchy
```

浏览器打开 http://127.0.0.1:4323/ 。源码页选择“Agent 提示词全集”。真实调用会产生 API 用量。

```bash
npm test
```

本轮原仓库 78 项离线测试通过。交付包未包含 .env、agents.json、历史运行数据、Git 目录和 Node 运行时；保留配置示例。

## 8. 推荐阅读顺序
先 server.mjs 的 /api/start，再 createPaperRun / executePaperRun，然后 prompts.mjs 和 agent-adapters.mjs，最后 console.mjs。阅读时围绕“输入来自哪里、调用谁、输出给谁、失败怎么办”四个问题。
