# 分层多智能体协作 Demo：完整说明与汇报稿

更新日期：2026-10-22。依据当前 `hierarchy-demo` 入口源码整理。

## 1. 一句话介绍

这是一个真实调用 DeepSeek 的分层多智能体协作原型：围绕摇摆户、营销、风控三个固定团队，选择协作拓扑、分配本题工作、按依赖交接消息，并通过质疑、审查、修订和隔离管理错误传播。

研究目标是验证“已有 Agent 如何协作”，而业务 Agent 的知识、工具和实际业务能力由另外的建设工作提供。当前通过同一个基础模型的不同职责提示和上下文模拟团队，尚未接入你们另一个平台已有 Agent 的接口、知识库或工具。

## 2. 总体运行结构

```text
浏览器：输入问题、选择方式、观察过程
  ↓ 本地 HTTP 接口
Node.js 后台：校验 → 路由 → 依赖调度 → 审查与恢复
  ↓ HTTPS / VPN TUN 或显式代理
DeepSeek：规划、分析、汇总、质疑、审查与进展评估
  ↓ 返回正文及可用的用量元数据
后台保存调用、事件、版本与结果 → 浏览器轮询展示
```

本机地址是 http://127.0.0.1:4323/ 。127.0.0.1 指自己的电脑，4323 是后台监听端口；后台未启动时打不开页面。页面不是部署在 GitHub 上的在线服务，GitHub 保存源码不等于后台持续运行。

## 3. 当前 Agent 与团队结构

| 团队 | 子角色 | 负责人作用 |
|---|---|---|
| 摇摆户 Agent | 需求与事实核查；行为与障碍分析 | 整合用户需求、事实、障碍及待验证假设 |
| 营销 Agent | 方案设计；效果评估 | 整合方案、实施条件、指标和对照设计 |
| 风控 Agent | 权限与边界；证据与承诺检查 | 整合权限、风险、事实依据和承诺边界 |

这里的六个子角色是演示职责，不是团队现有子 Agent 的已验证映射。一个角色是职责提示、当前上下文和模型请求的组合，并非独立训练的大模型，也不是九个单独部署的服务。

身份注册表由程序控制，模型不得创造组织发展师等新顶层身份。顶层本题任务可以随问题调整，子角色基本职责固定。当前三队全部参与，尚未按能力动态减少参与团队。

校招生业务参与问题并不完全适配这三队：需求团队只能做事实澄清，营销团队只能从业务参与和试点设计切入，风控团队检查权限与依据。不能把校招生当摇摆户，也不能因此宣称具备组织人才专业能力。

## 4. 规划、路由与调度

- 规划：确定协作方式，并向现有团队分派本题工作。
- 角色分工：约束谁承担什么职责，不能擅自创建身份。
- 路由：确定消息依赖、先后关系；链式还确定团队顺序。
- 调度：由程序检查依赖、排队、启动模型请求、控制并发、预算与取消。

当前只有 DeepSeek 一个模型候选，没有多模型择优。模型可以提出计划，但执行图必须通过程序校验。

### 路由来源

| 来源 | 当前行为 | 局限 |
|---|---|---|
| 手动拓扑 | 用户指定五种方式之一 | 指定结构不一定指定链式先后 |
| LLM 自动选图 | 提交问题、名册和候选拓扑，返回方式、理由及分工 | 增加推理成本，可能选错；不是训练后的 MasRouter |
| 规则选图 | 敏感/授权关键词优先风控先行；客户营销类需求先行；其余并行 | 人工关键词基线，不保证最优 |
| 训练控制器 | 未接入 | 尚无通过业务评测的路由权重与多场景效果证明 |

规划结构不合格时最多一次显式结构纠正；仍无效可记录警告并显式回退固定并行基线。网络故障不会伪装成成功规划。

## 5. 五种协作方式

| 拓扑 | 实际信息关系 | 考虑因素 |
|---|---|---|
| 并行会诊 | 三队独立首轮分析，再综合 | 减少前序观点锚定，可能保留冲突 |
| 动态链式 | 按题意选 A→B→C，B读A，C读A和B的已审查结论 | 逐级细化；顺序不再写死 |
| 需求先行 | 摇摆户→营销、风控 | 先澄清需求，后两队独立推进 |
| 风控先行 | 风控→摇摆户、营销 | 先确定边界，后续仍可能产生新风险 |
| 多轮交叉辩论 | 独立初稿→按轮互读上轮结论、回应、更新和复审→综合 | 对分歧进行额外处理，成本更高 |

逻辑并行不等于所有请求同时发出：后台最多同时两个模型请求。同一队的子任务、汇总和审查有依赖关系。轨迹最新事件在上面，列表顺序不能用来证明串行；判断并行应查看实际请求时间区间。

## 6. 动态链式：此次新增内容

默认由当前选定路由器决定链式顺序。LLM 结合具体问题、团队职责返回顺序和理由；规则基线提供明确可审计的选择：

- 涉及生产、敏感、隐私、授权或客户数据：风控→摇摆户→营销。
- 对已有/现有方案做评审或优化：营销→摇摆户→风控。
- 其他：摇摆户→营销→风控。

这三条是当前规则的启发式，不是业务最优结论。LLM 不必机械照搬。

如果自动选图请求已经返回合法的链式顺序，直接复用；如果用户手选链式且顺序自动、路由器为LLM，则额外调用一次顺序路由器。可在高级设置中手动指定六种合法排列，用于同题对照。手动顺序优先。

程序校验三个团队各出现一次，拒绝遗漏、重复和非法身份。生成图时，后续团队依赖前面全部团队的审查结果。看板的关系图、执行阶段、实际顺序、选序来源和理由来自本任务数据。

例如“客户数据授权未确认，先确定边界，再设计试点”，可以选择风控→摇摆户→营销。风控先给约束，摇摆户在约束内分析需求，营销再结合二者给方案。

顺序在本次执行前确定，并非执行中任意跳转。跨团队退回补充信息、局部重排与断点续跑尚未实现。Inspector 退回原作者改正文属于已有修订回路，不等同跨团队重新调度。无论谁最后发言，最终综合仍有 Inspector。

## 7. 汇总与质疑、Inspector 的区别

负责人读取本队子材料及允许的上游结论，整合内容、检查分歧，形成团队答案；Inspector 通过另一请求检查这份成稿是否达到交接条件。

```text
两个子角色 → 负责人整合与质疑 → 团队候选
                                  ↓
                              Inspector
                         通过 ↙       ↘ 实质问题
                         交接        原角色修订 → 再审查
```

子输出先进入负责人上下文，不是每条子输出都单独经过 Inspector。风控是产出风险分析的业务角色；Inspector 是对任意团队消息执行交接检查的审查职责。

Inspector 与执行者共用同一基础模型。“独立”指职责与调用分开，不代表错误统计独立，更不等于外部事实核验。原文定位也只能说明意见有对应位置，不能证明审查正确。

## 8. 消息审查和错误恢复

一般细节不足、重复、补充数据建议不会直接阻断。实质问题包括未知当事实、明确矛盾、虚称已执行、越权操作建议、完全未回答题目。要求认可的类别、major/critical严重程度和原文逐字引用，才进入修订。

候选与审查均保留版本。最多两次内容修订、三次审查；仍未通过时隔离原文，只向下游提供缺失说明。最终答案仍有实质问题则待人工复核，不显示已批准交付。

网络失败不自动重试；格式无效最多一次可见纠正，产生实际调用费用。初始团队阶段可保留成功子材料，整个分支失败则隔离团队；全部团队不可用则停止综合。取消通过AbortSignal传递，但提供方已经处理的请求仍可能计费。

隔离是应用层上下文控制，不是操作系统沙箱。模型输出不会自动变成真实执行动作，当前没有银行生产工具权限。

## 9. 多轮辩论与自动结束

初稿不计入辩论轮。每轮三队读取同一份上一轮已审查快照，回应质疑、写出修改与未解决问题，并给出更新后的完整结论。整轮结束后才进入下一轮，避免同一轮受发言先后影响。

本轮新候选失败则保留该队上一轮已审查结论，并记录警告。每轮保存前后快照、分支状态、模型正文、调用和审查版本。

默认自动结束，无需用户选择轮数。每轮另有进展评估请求，比较前后材料、回应、实质修改、未回答质疑和未解决问题；未解决问题要求原文定位，并说明是否可在当前材料下继续解决。可处理问题送入下轮focus。

程序会检查评估字段、原文定位、停止结论与未解决问题是否冲突；完全相同的答案或连续两轮评估无实质修改会停止。停止原因区分：稳定、无进展、需外部信息、部分材料缺失、达到轮数上限、预算限制或评估不可用。

自动模式仍有3轮、总计48次请求的兜底上限。停止不代表达成共识或事实正确；最终综合读取停止原因和未解决问题，仍需最终审查。高级设置保留固定1—3轮对照模式。自动判断是工程启发式加LLM评估，可能误判，不是数学收敛保证，也不是强化学习。

## 10. 看板各模块的作用

| 模块 | 用途与注意点 |
|---|---|
| API调用证据 | 展示真实HTTP状态、提供方响应ID、返回模型、时间、usage、耗时及网络；默认取最近成功记录，可能来自另一任务 |
| 连接验证 | 点击才发起一次真实请求，有费用；历史成功不能保证此刻网络正常 |
| 任务控制 | 输入问题，选自动/手动拓扑及路由器，启动或停止；高级设置提供辩论和链式对照选项 |
| 拓扑卡片 | 用文字关系解释五种结构，并高亮下一次任务的选择 |
| 实际拓扑图 | 展示当前任务真实依赖，不会因为更改下次选项就改写历史图；箭头表示审查后的交接 |
| 节点详情 | 查看子任务、负责人、审查和本题分工，点击进入调用详情 |
| 指标卡片 | 调用记录数、API返回token、实际协作方式、已放行版本数；放行数不是Agent数量 |
| 逐轮记录 | 查看每轮回应、修改、结果快照、独立审查和进展评估 |
| 事件与消息轨迹 | 时间戳和序号显示排队、调用、隔离、修订、继续/停止、交付或失败 |
| 详情面板 | 真实输入输出、提示、用量、消息版本；不是模型隐藏思维链 |
| 最终交付 | 摘要、行动、假设、限制和警告；阶段结果不等同最终批准答案 |
| 运行历史与导出 | 最近20个任务及JSON导出；旧角色与旧失败保持原样 |
| 论文与源码页 | 研究依据、工程边界和白名单源码，不提供密钥文件读取 |

## 11. 技术与文件对应

| 文件 | 技术与职责 |
|---|---|
| console.html / console.css | HTML、CSS控制台，拓扑卡片与响应式布局 |
| console.mjs | 原生JavaScript、DOM、SVG关系图、HTTP fetch；约1.5秒轮询，不是WebSocket或SSE |
| server.mjs | Node.js原生HTTP服务、同源校验、输入限制、任务启动/停止、配置重读和历史持久化 |
| paper-runtime.mjs | 自定义异步状态机，名册、依赖图、Promise.allSettled、并发排队、修订、辩论及动态选序 |
| model-provider.mjs | DeepSeek Chat Completions适配、JSON输出要求、完整响应检查、用量与证据保存；非流式、thinking关闭 |
| model-transport.mjs | 原生HTTPS、取消、超时及响应大小限制，不自动重试网络调用 |
| model-network.mjs | 环境HTTP(S)代理、已启用Windows系统代理、无显式代理时走系统网络/VPN TUN |
| data/hierarchy-v2/state.json | 本地JSON运行记录，串行写入临时文件再替换；Windows文件占用时有限重试文件替换，不重发模型请求 |
| *.test.mjs | Node自带测试框架，模拟模型及错误，验证编排规则 |

当前未使用LangGraph、AutoGen、数据库、向量检索或RAG；同一个后台一次运行一个用户任务，任务内部请求最多两个并发。

接口：GET /api/state 查询状态；POST /api/start 启动；POST /api/cancel 停止；POST /api/reload 重读配置；POST /api/probe 连接验证；GET /api/source 读取白名单源码。旧演化接口保留，但当前paper-live任务没有接入旧演化流程。

## 12. 启动、网络与数据边界

在项目目录运行 `node hierarchy-demo/server.mjs` 或 `npm run hierarchy`，再打开4323地址。已有.env不要覆盖。密钥只在本地.env配置；页面加载不自动验证API、不自动发付费任务。

代理自动模式依次考虑显式LLM_PROXY_URL、代理环境变量、已启用Windows代理；没有则走系统网络，可能经VPN TUN。需要显式HTTP(S)代理时使用Node24.14+；不自动切VPN、不过滤证书校验、不支持SOCKS/PAC直接配置。本机地址绕过代理。

密钥不返回前端。任务、上下文和模型结果会发送到所配置的模型服务；这是本地界面加远程模型，不能当成离线私有推理。历史和导出包含问题正文，分享前检查业务信息。服务仅监听本机，尚无面向多人公网部署的登录、权限体系。

## 13. 调用、成本与限制

普通无修订执行14次：6子角色+3负责人+3团队审查+1综合+1最终审查。

- 自动选图通常另加1次。
- 手选链式、LLM自动选序通常另加1次；已有选图返回合法顺序则复用，不重复选序。
- 固定辩论每轮通常另加6次；自动结束辩论每轮通常另加7次（含进展评估）。
- 格式纠正和内容修订额外计数，均在记录中可见。

总预算48条请求记录，普通输出最多3000 token，最终最多5000；单请求总体超时180秒。预算预留仅保证基础调用额度，不保证修订后一定有足够额度完成；耗尽会停止并保留已接受结果。

记录数可能含排队或未发送请求；token仅统计提供方已返回usage，不是人民币费用，故障请求是否计费可能未知。

## 14. 论文对应与研究边界

[MasRouter（ACL 2025）](https://aclanthology.org/2025.acl-long.757/)提供协作方式、角色与模型的级联路由研究框架。当前采用阶段化思路，但角色固定、单模型，由LLM或规则选择，并未部署训练后的原版控制器。

[MAS-Resilience（ICML 2025）](https://proceedings.mlr.press/v267/huang25ay.html)研究错误Agent传播，提出Challenger和Inspector。当前借鉴质疑和消息审查；分级意见、两次修订、自动结束、预算与动态链式是本项目工程设计，未复现论文故障注入基准或恢复率。

当前没有跨任务自动更新提示、长期记忆或路由权重。本任务的修订和多轮辩论不等于自进化。未来训练小型路由控制器可行，但需要真实效果和成本数据、未见场景测试及上线回滚，不应直接把模型自评当业务奖励。

## 15. 当前证据和后续评测

动态链式新增回归后，本地75项离线测试通过，覆盖六种顺序依赖、非法名册、LLM选序、复用规划、规则选序、前序审查后再推进，以及原有辩论、隔离、取消、API适配等。

这不是75道真实业务题正确率。已有真实API回放证明流程可以运行，成功也可能含警告；历史网络失败同样保留。本次动态链式真实验证：数据授权未确认的问题，LLM选择风控→摇摆户→营销；15次请求，返回用量30,794 token，含审查建议交付。此单例证明按选序执行，不证明顺序最优。记录另存本机 `data/dynamic-chain-validation.json`，不上传仓库。

后续应接真实业务Agent接口，使用同一批代表性任务比较单Agent、固定结构、LLM动态路由和规则基线。由业务人员盲评正确性、可执行性、权限问题，同时记录token、耗时、失败率、错误漏放和误阻断。未完成对照前，不能宣称多Agent更优、更便宜或具备跨场景泛化。

## 16. 汇报演示顺序与口述稿

建议先展示一个权限与营销目标有冲突的问题，再展示选路理由和实际箭头，点开一条前序审查及后序输入，证明材料确实按图传递；如演示辩论，再点逐轮记录及停止原因，最后看答案和限制。优先用已完成记录，避免把演示时间押在网络响应上。

可口述：

> 我们完成的是一个论文启发的分层多智能体协作与可靠性交互原型。它按摇摆户、营销、风控三个固定团队组织任务，真实调用DeepSeek，支持五种拓扑。链式顺序现在按问题动态选择，涉及数据授权可先风控，已有方案可先营销，并展示理由和实际依赖。负责人负责形成答案，Inspector负责交接检查，实质错误会修订复审或隔离。多轮辩论默认自动判断继续或结束，记录未解决问题，同时保留预算与轮数上限。当前角色由同一模型的不同职责提示实现，尚未接入真实业务Agent，也没有训练原版MasRouter或实现跨任务自进化。下一步重点是接真实能力和同题对照评测，再验证效果与成本收益。
